01 / What changes

Automatic identity, explicit authentication

Today

~/.gitconfig is a symlink to ~/.dotfiles/.gitconfig. It always includes ~/.gitconfig.work.local, so work is the global default.

Dotfiles overrides its identity locally to rushjs1 <rushjsdev@gmail.com>. Its origin already uses git@github-personal:rushjs1/.dotfiles.git.

Proposed

Load personal identity first. Repositories whose Git directory is under ~/work/ then load the work identity.

Keep dotfiles at ~/.dotfiles. Personal projects can remain where they are, outside ~/work/. A separate personal folder is optional.

Changing one selector does not automatically change the others. Directory-based identity also applies to work repositories hosted on Azure DevOps.

Observed locally: global/local Git settings, SSH host blocks, origin URL, installer, and account skills. Key ownership on GitHub and the current CLI login were not authenticated during planning. The expected work account rushjs2 comes from your existing work skill.

02 / Proposed files

The Git configuration, line by line

Use ~/work/, meaning /Users/johnrush/work/. The leading tilde matters: /work would instead be a directory at the filesystem root.

Tracked: ~/.dotfiles/.gitconfig

[core]
    editor = nvim

[include]
    path = ~/.gitconfig.personal.local

[includeIf "gitdir:~/work/"]
    path = ~/.gitconfig.work.local
  • [core] groups Git’s basic settings; editor = nvim preserves your existing editor.
  • [include] loads another configuration unconditionally. Its path makes personal identity the starting value.
  • [includeIf "gitdir:~/work/"] loads its file only when the Git directory matches. The trailing slash includes nested directories.
  • The second path loads the existing work identity after personal values, so matching work values win.
  • Blank lines only separate sections for readability. The current installer’s symlink remains correct; editing the tracked file changes the live global configuration immediately.

New local personal file

# ~/.gitconfig.personal.local
[user]
    name = rushjs1
    email = rushjsdev@gmail.com

[user] groups identity settings. name is the commit display name, not an authentication setting; email is the author/committer email. These preserve the personal identity already used in dotfiles.

Existing local work file

# ~/.gitconfig.work.local
[user]
    name = John Rush
    email = john.rush@e-gineering.com

Keep these values. Only the circumstances under which the file is included change. The account used for SSH is selected separately.

The two local files stay in your home directory, outside the dotfiles repository. Their .local suffix is a naming convention, not automatic Git protection. On a new machine they must be provisioned explicitly; the installer currently only links the global config.

Precedence and exceptions

Repository-local identity values override the directory defaults. Command-line settings and author/committer environment variables can also override the result. Audit these before treating a folder move as sufficient. Keep intentional exceptions; remove redundant local values only after verifying the new defaults.

The rule follows the Git metadata location. A linked worktree outside ~/work/ can still use work identity when its main repository lives inside it. Conversely, putting only a linked worktree in ~/work/ does not necessarily select work. Verify each linked worktree. Git conditional include documentation.

03 / GitHub authentication

Reuse your keys. Name both accounts.

No SSH change is required just to enable directory-based commit identity. For clarity, the recommended companion change adds github-work as another name for your current work host. Keep github.com working as it does today.

# ~/.ssh/config — proposed GitHub blocks only
Host github.com github-work
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_github
    IdentitiesOnly yes
    UseKeychain yes
    AddKeysToAgent yes

Host github-personal
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_github_personal
    IdentitiesOnly yes
    UseKeychain yes
    AddKeysToAgent yes

Host github.com github-workThe only proposed SSH edit: add github-work to the existing work block. Both hostnames select the same settings. Existing ordinary GitHub SSH remotes remain compatible.
Host github-personalPreserves your existing personal alias. The alias is local to your SSH configuration, not a separate GitHub server.
HostName github.comBoth aliases connect to GitHub’s actual server.

AddKeysToAgent yesLets SSH add a loaded key to the running agent for reuse.

Leave the existing Host ssh.dev.azure.com block and Azure key unchanged. This plan does not add signing keys or commit-signing settings.

Remote URLs become self-explanatory

# Personal — dotfiles already has this URL
git@github-personal:rushjs1/.dotfiles.git

# Work — substitute the real owner and repository
git@github-work:WORK_OWNER/REPOSITORY.git

The owner after the colon is the repository owner or organization; it does not have to equal the authenticating account. For a migrated work repository, a future command would be:

git -C ~/work/REPOSITORY remote set-url origin \
    git@github-work:WORK_OWNER/REPOSITORY.git

Record the original URL first. Check every remote and any separate push URL, not just origin. HTTPS remotes use credential helpers instead of these SSH blocks; convert selected repositories deliberately or keep their HTTPS authentication workflow. Avoid broad URL rewrites in the first migration.

Cloning still needs the right alias

Use git clone git@github-work:WORK_OWNER/REPOSITORY.git ~/work/REPOSITORY for work. Use github-personal for personal clones. An ordinary git@github.com:… URL continues to select the work key even outside ~/work/. The folder rule does not route SSH.

Before implementation, confirm the work key authenticates as rushjs2 and the personal key as rushjs1. If either fails, verify its matching public key is registered to the intended GitHub account and, where required, authorized for the organization’s SSO. Do not assume a filename proves key ownership.

04 / PRs and API calls

GitHub CLI keeps its own login

Neither includeIf nor SSH aliases switches the active account for gh. When both accounts are already logged in, select the appropriate account before account-sensitive CLI work:

# Future work session
gh auth switch --hostname github.com --user rushjs2

# Future personal session
gh auth switch --hostname github.com --user rushjs1

# Verify the account actually used by the API
gh api user --jq .login

--hostname refers to the real GitHub API host, not your SSH alias. --user chooses a stored login. Switching changes the active CLI account for that host across sessions, so avoid competing switches during simultaneous work/personal tasks. Environment tokens such as GH_TOKEN or GITHUB_TOKEN can take precedence; verify the actual API identity without printing token values.

Keep your personal and work skills as verification guidance. A future documentation update can explain the directory and alias conventions; their requirements to check identity and obtain explicit commit/push authorization remain useful. GitHub CLI account switching.

05 / Implementation sequence, for later

Migrate one repository first

1. Inventory and save a rollback record

List all work repositories, their paths, remotes and push URLs, local identity overrides, linked worktrees, and tools that refer to their paths. Check dirty files and active processes. Save the current global Git file, local identity files, SSH config, and per-repository settings being changed to a dated local backup. Do not copy private keys into the dotfiles repository.

2. Prepare the new settings without switching defaults

Create the personal local file and add the work SSH alias. Verify both SSH accounts. Create ~/work/. Keep the current global work default while work repositories are still scattered.

3. Move work repositories carefully

Start with one ordinary work clone and verify it after moving. Move the remaining work clones before changing the global default. For a work repository that must stay outside the folder, explicitly retain or set its work identity locally as a documented exception.

Update editor workspaces, terminal shortcuts, scripts, dev-server paths, and T3 project references. If a repository is served through Laravel Valet, account for its parked or linked path. Handle linked worktrees using Git-aware move/repair procedures and verify their registration; do not bulk-move them blindly.

4. Enable the conditional include

Edit the tracked global Git file to the proposed content. Its home-directory symlink makes the change live immediately. Keep dotfiles and personal repositories outside the work folder. Verify identity before removing any redundant repository overrides.

5. Standardize URLs and document setup

Use github-work for work SSH remotes and keep github-personal for personal remotes. Validate separate push URLs and submodules individually; avoid committing machine-specific aliases to shared .gitmodules without team agreement. Document local-file provisioning for fresh machines; no installer rewrite is needed for the existing global symlink.

6. Complete the verification matrix

Run the checks below on personal, work, exception, and linked-worktree repositories. Stop after verification. Committing or pushing requires a separate explicit instruction.

08 / Decisions for the later review

Recommended defaults to approve later

Folder & fallback

Use ~/work/ and personal identity elsewhere. Accept that a misplaced work clone will inherit personal identity unless locally overridden.

Alternative: explicit work and personal roots with no default identity and user.useConfigOnly = true. More restrictive, but requires classifying dotfiles and other personal locations. Not the proposed baseline.

SSH compatibility

Add github-work while preserving github.com as work. This avoids changing the meaning of existing remotes.

Changing ordinary github.com to personal would need a separate audit of every affected remote and tool. It is not needed for this migration.

Personal display name

Keep rushjs1 to match your existing personal repository and skill. Changing it to John Rush is an optional preference, independent of authentication.

Repository move list

Confirm the actual work inventory and any exceptions when implementation starts. This planning pass did not crawl all project directories or authenticate either key.
